# Техническое задание TaskManager ("аля Jira Light")

## 1. Цель проекта
Создать backend‑систему управления задачами с поддержкой workspace, project, board и task, построенную на принципах **DDD**, **чистой архитектуры** и строгих доменных инвариантов.

Система должна обеспечивать:

- изоляцию workspace
- ролевую модель доступа
- workflow задач
- историю изменений
- минимальную связность между агрегатами
- расширяемость (возможность добавлять новые workflow, роли, типы задач)

---

# 2. Архитектура домена

## 2.1. Агрегаты и их границы

### IdentityAggregate

Корень: User  
Внутренние сущности: нет  
Внешние связи: UserId используется другими агрегатами

Инварианты:

- email уникален.
- Пользователь может находиться в статусе ACTIVE/DEACTIVATED.
- Пользователь не может быть деактивирован или удалён, если является OWNER хотя бы одного Workspace.
- Пользователь может состоять в нескольких Workspace.

### WorkspaceAggregate

Корень: Workspace  
Внутренние сущности: нет  
Внешние связи: OwnerUserId

Инварианты:

- Workspace всегда имеет OWNER.
- Workspace может находиться в статусе ACTIVE/USER_ARCHIVED.
- Архивированный Workspace не может быть изменён.
- Передача владения возможна только существующему участнику Workspace.
- OWNER не может быть удалён или деактивирован без передачи владения другому пользователю.

### WorkspaceMembershipAggregate

Корень: WorkspaceMember  
Внутренние сущности: нет
Внешние связи: WorkspaceId, UserId

Инварианты:

- Для пары (WorkspaceId, UserId) может существовать только один WorkspaceMember.
- WorkspaceMember может быть создан только для существующего User.
- WorkspaceMember может быть создан только для существующего Workspace.
- WorkspaceMember может иметь роль OWNER, ADMIN или MEMBER.
- WorkspaceMember может быть заблокирован пользователем с ролью ADMIN или OWNER.
- WorkspaceMember архивируется при деактивации User.
- WorkspaceMember не может быть изменён, если связанный Workspace архивирован.

### ProjectAggregate

Корень: Project  
Внутренние сущности: нет
Внешние связи: WorkspaceId

Инварианты:

- Project принадлежит Workspace.
- Project не может быть создан без существующего Workspace.
- Project может находиться в статусе ACTIVE/USER_ARCHIVED/PARENT_ARCHIVED.
- Project архивируется при архивации Workspace.
- Архивированный Project не может быть изменён.

### BoardAggregate

Корень: Board  
Внутренние сущности: BoardColumn  
Внешние связи: ProjectId

Инварианты:

- Board принадлежит Project.
- Колонки имеют уникальный порядок внутри Board.
- Колонка не может быть удалена, если содержит задачи.
- Board архивируется при архивации Project или Workspace.
- Архивированный Board не может быть изменён.

### TaskAggregate

Корень: Task  
Внутренние сущности: Comment, Tag, AuditEntry

Внешние связи: BoardId, AssigneeUserId

Инварианты:

- Task принадлежит Board.
- Статус Task должен соответствовать workflow.
- Исполнитель должен являться активным участником Workspace.
- AuditEntry создаётся при изменении значимых полей задачи.
- Task архивируется при архивации Board, Project или Workspace.
- Архивированная Task не может быть изменена.
- Что мне особенно нравится в таком варианте

# 3. Сущности и связи

### Workspace / Project / Board / Task
Все связи между агрегатами — **через UUID**, без JPA‑отношений.

Причины:
- слабая связность
- независимые транзакции
- отсутствие каскадных удалений
- возможность вынести агрегаты в отдельные bounded context

### Внутренние сущности
- WorkspaceMember — часть Workspace
- BoardColumn — часть Board
- Comment/Tag/AuditEntry — часть Task

### Корректировки:
- Tag лучше сделать частью TaskAggregate, а не отдельным агрегатом
- AuditEntry должен быть неизменяемым (immutable)
- Comment должен иметь собственный идентификатор, но жить внутри Task

---

# 4. Ролевая модель доступа

### Workspace
OWNER / ADMIN / MEMBER

### Правила доступа
- Доступ к Task определяется доступом к Board → Project → Workspace
- Пользователь не может видеть сущности вне своих workspace
- Все проверки выполняются в доменных сервисах
- Контроллеры не содержат бизнес‑логики

### Дополнение:
- OWNER может назначать ADMIN
- OWNER/ADMIN может менять структуру доски

---

# 5. Workflow задач (под сомнением, пока что пропустим)

### Базовый workflow
```
TODO → IN_PROGRESS → DONE
TODO → BLOCKED → TODO
IN_PROGRESS → BLOCKED → IN_PROGRESS
```

### Дополнения:
- Workflow должен быть расширяемым
- Переходы валидируются доменным сервисом WorkflowService
- Task.changeStatus() вызывает WorkflowService.validateTransition()

# 6. Требования к API

### User API
- регистрация пользователя
- получение профиля
- деактивация пользователя

### Workspace API
- создание workspace
- добавление участника
- назначение роли
- получение списка проектов
- получение списка участников

### Project API
- создание проекта
- архивирование
- получение списка досок
- изменение названия/описания

### Board API
- создание доски
- настройка колонок
- получение задач
- изменение порядка колонок

### Task API
- создание задачи
- изменение полей
- смена статуса
- назначение исполнителя
- добавление комментария
- добавление тега
- просмотр истории
- фильтрация по статусу/исполнителю/тегам

### Дополнения:
- API должен быть RESTful
- Версионирование `/api/v1/...`
- Единый формат ошибок
- Пагинация списков
