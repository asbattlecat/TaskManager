# Техническое задание TaskManager ("аля Jira Light")

## 1. Цель проекта
Создать backend‑систему управления задачами с поддержкой workspace, project, board и task, построенную на принципах **DDD**, **чистой архитектуры** и строгих доменных инвариантов.

Система должна обеспечивать:

- изоляцию workspace
- ролевую модель доступа
- workflow задач
- историю изменений
- минимальную связность между агрегатами
- расширяемость (возможность добавлять новые workflow, роли, типы задач)

---

# 2. Архитектура домена

## 2.1. Агрегаты и их границы

### IdentityAggregate
Корень: User  
Внутренние сущности: нет  
Внешние связи: UserId используется всеми другими агрегатами  
Инварианты:  
- email уникален
- пользователь может быть активным/деактивированным
- пользователь не может быть удалён, если он является OWNER workspace
- User может быть участником нескольких workspace

### WorkspaceAggregate
Корень: Workspace  
Внутренние сущности: WorkspaceMember  
Внешние связи: только UUID  
Инварианты:
- Workspace имеет OWNER
- WorkspaceMember уникален по userId
- OWNER не может быть удалён без передачи роли
- WorkspaceMember создаётся только для существующего User
- WorkspaceMember удаляется при деактивации User

### ProjectAggregate
Корень: Project  
Внутренние сущности: нет  
Инварианты:
- Project принадлежит Workspace
- Project не может быть создан без существующего Workspace
- Project может быть в статусе ACTIVE/ARCHIVED

### BoardAggregate
Корень: Board  
Внутренние сущности: BoardColumn  
Инварианты:
- Колонки имеют уникальный порядок (sequence)
- Колонка не может быть удалена, если в ней есть задачи
- Board принадлежит Project

### TaskAggregate
Корень: Task  
Внутренние сущности: Comment, Tag, AuditEntry  
Инварианты:
- Статус валиден согласно workflow
- Исполнитель должен быть членом Workspace
- Task принадлежит Board → Project → Workspace
- AuditEntry создаётся при каждом изменении значимых полей
- Tag уникален в пределах Task

# 3. Сущности и связи

### Workspace / Project / Board / Task
Все связи между агрегатами — **через UUID**, без JPA‑отношений.

Причины:
- слабая связность
- независимые транзакции
- отсутствие каскадных удалений
- возможность вынести агрегаты в отдельные bounded context

### Внутренние сущности
- WorkspaceMember — часть Workspace
- BoardColumn — часть Board
- Comment/Tag/AuditEntry — часть Task

### Корректировки:
- Tag лучше сделать частью TaskAggregate, а не отдельным агрегатом
- AuditEntry должен быть неизменяемым (immutable)
- Comment должен иметь собственный идентификатор, но жить внутри Task

---

# 4. Ролевая модель доступа

### Workspace
OWNER / ADMIN / MEMBER

### Project
PROJECT_ADMIN / PROJECT_MEMBER

### Board
BOARD_ADMIN / BOARD_MEMBER / BOARD_VIEWER

### Правила доступа
- Доступ к Task определяется доступом к Board → Project → Workspace
- Пользователь не может видеть сущности вне своих workspace
- Все проверки выполняются в доменных сервисах
- Контроллеры не содержат бизнес‑логики

### Дополнение:
- OWNER может назначать ADMIN
- ADMIN может назначать PROJECT_ADMIN
- BOARD_ADMIN может менять структуру доски

---

# 5. Workflow задач

### Базовый workflow
```
TODO → IN_PROGRESS → DONE
TODO → BLOCKED → TODO
IN_PROGRESS → BLOCKED → IN_PROGRESS
```

### Дополнения:
- Workflow должен быть расширяемым
- Переходы валидируются доменным сервисом WorkflowService
- Task.changeStatus() вызывает WorkflowService.validateTransition()

# 6. Требования к API

### User API
- регистрация пользователя
- получение профиля
- деактивация пользователя

### Workspace API
- создание workspace
- добавление участника
- назначение роли
- получение списка проектов
- получение списка участников

### Project API
- создание проекта
- архивирование
- получение списка досок
- изменение названия/описания

### Board API
- создание доски
- настройка колонок
- получение задач
- изменение порядка колонок

### Task API
- создание задачи
- изменение полей
- смена статуса
- назначение исполнителя
- добавление комментария
- добавление тега
- просмотр истории
- фильтрация по статусу/исполнителю/тегам

### Дополнения:
- API должен быть RESTful
- Версионирование `/api/v1/...`
- Единый формат ошибок
- Пагинация списков
