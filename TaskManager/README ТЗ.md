# Менеджер задач — Техническое задание (ТЗ)

## 1. Цель проекта

Создать современный, расширяемый и архитектурно корректный backend‑сервис для управления задачами. Система должна обеспечивать создание, хранение, фильтрацию, сортировку, изменение и аудит задач, а также поддержку пользователей, ролей и JWT‑аутентификации.

Проект ориентирован на обучение промышленным практикам разработки: чистая архитектура, доменная модель, DTO, маппинг, Spring Security, JPA, миграции, тестирование.

## 2. Архитектурные требования

### 2.1. Общая архитектура

Проект должен следовать слоистой архитектуре:

- **Domain** — доменные сущности, value objects, бизнес‑правила.
- **Repository** — доступ к данным, интерфейсы JPA.
- **Service** — бизнес‑логика, транзакции, сценарии использования.
- **Controller** — REST API, DTO, валидация.
- **Mapper** — преобразование DTO ↔ Domain (MapStruct).

### 2.2. Принципы

- Доменные сущности не должны зависеть от инфраструктуры.
- Контроллеры не содержат бизнес‑логики.
- Сервисы не содержат логики представления.
- Репозитории не содержат бизнес‑логики.
- DTO не содержат бизнес‑логики.

## 3. Функциональные требования

### 3.1. Задачи

Задача должна содержать:

- ID
- Заголовок
- Описание
- Статус (TODO, IN_PROGRESS, DONE, BLOCKED)
- Приоритет (LOW, MEDIUM, HIGH, CRITICAL)
- Исполнителя (пользователь)
- Дедлайн
- Дату создания
- Дату обновления
- Теги
- Подзадачи
- Историю изменений

- Сортировка по приоритету, дедлайну, дате создания
- Добавление комментариев

### 3.3. Комментарии

### 3.4. Теги

- новое значение

# README — Техническое задание  
## Проект: Workspace–Project–Board Task Manager

---

## 1. Цель проекта

Создать backend‑систему уровня «Jira Light», в которой пользователи работают внутри **workspace**, организуют работу по **project**, визуализируют задачи на **board** и управляют **task** с учётом ролей, прав доступа, статусов, приоритетов и истории изменений.

Проект ориентирован на прокачку:

- архитектурного мышления  
- проектирования доменной модели  
- ролевой модели доступа  
- работы с транзакциями и бизнес‑правилами  
- тестируемости и чистой архитектуры  

---

## 2. Общая концепция домена

### 2.1. Основные сущности

- **Workspace** — пространство/организация, в рамках которой работают пользователи.  
- **Project** — логическая единица работы внутри workspace (продукт, направление, фича).  
- **Board** — доска задач (канбан, спринт, backlog) внутри проекта.  
- **Task** — единица работы на доске.  
- **User** — пользователь системы.  
- **Membership / Role** — участие пользователя в workspace/project/board с определённой ролью.  
- **Comment** — комментарий к задаче.  
- **Tag** — метка для классификации задач.  
- **Audit / HistoryEntry** — запись об изменении задачи.

### 2.2. Иерархия сущностей

- `Workspace`  
  - содержит множество `Project`  
  - содержит множество `WorkspaceMember` (User + роль)

- `Project`  
  - принадлежит `Workspace`  
  - содержит множество `Board`

- `Board`  
  - принадлежит `Project`  
  - содержит множество `Task`  
  - может иметь настройки (колонки, workflow)

- `Task`  
  - принадлежит `Board`  
  - имеет исполнителя (`User`)  
  - может иметь подзадачи, теги, комментарии, историю изменений

---

## 3. Ролевая модель и доступы

### 3.1. Уровни доступа

**Уровень Workspace:**

- `WORKSPACE_OWNER` — владелец пространства  
- `WORKSPACE_ADMIN` — управляет участниками, проектами  
- `WORKSPACE_MEMBER` — обычный участник

**Уровень Project (опционально):**

- `PROJECT_ADMIN`  
- `PROJECT_MEMBER`

**Уровень Board (опционально):**

- `BOARD_ADMIN`  
- `BOARD_MEMBER`  
- `BOARD_VIEWER`

### 3.2. Принципы доступа

- Доступ к `Task` определяется доступом к её `Board` → `Project` → `Workspace`.  
- Пользователь не может видеть/изменять сущности вне своих workspace/project/board.  
- Операции над задачами (создание, изменение, удаление, смена статуса, назначение исполнителя) разрешены только при наличии соответствующей роли.

---

## 4. Пользовательский опыт (UX)

### 4.1. Основные сценарии

1. Пользователь входит в систему (JWT).  
2. Видит список доступных workspace.  
3. Выбирает workspace → видит список проектов.  
4. Выбирает проект → видит список досок.  
5. Выбирает доску → видит задачи.  
6. Работает с задачами:  
   - создаёт  
   - изменяет  
   - перемещает по статусам  
   - фильтрует  
   - сортирует  
   - комментирует  

### 4.2. Дополнительные сценарии

- Переключение между workspace.  
- Просмотр «моих задач» (по исполнителю).  
- Фильтрация по статусу, приоритету, тегам, дедлайну.  
- Просмотр истории изменений задачи.  

---

## 5. Функциональные требования

### 5.1. Workspace

**Требования:**

- Создание workspace.  
- Приглашение пользователей в workspace.  
- Назначение ролей на уровне workspace.  
- Просмотр списка проектов в workspace.  

**Инварианты:**

- Workspace не может существовать без владельца.  
- Пользователь может иметь разные роли в разных workspace.

---

### 5.2. Project

**Требования:**

- Создание проекта внутри workspace.  
- Просмотр списка проектов.  
- Управление проектами (переименование, архивирование).  

**Инварианты:**

- Project всегда принадлежит одному workspace.  
- Удаление workspace недопустимо без обработки связанных проектов.

---

### 5.3. Board

**Требования:**

- Создание доски внутри проекта.  
- Настройка типа доски (kanban, sprint, backlog).  
- Настройка колонок/статусов (для kanban).  
- Просмотр списка досок проекта.  

**Инварианты:**

- Board всегда принадлежит одному проекту.  
- Task не может существовать вне board.

---

### 5.4. Task

**Требования:**

- Создание задачи на доске.  
- Обновление задачи (title, description, priority, assignee, tags, deadline).  
- Смена статуса задачи (workflow).  
- Назначение исполнителя.  
- Добавление подзадач.  
- Фильтрация и сортировка задач.  
- Просмотр истории изменений.  

**Инварианты:**

- Task принадлежит одной board.  
- Статус задачи должен соответствовать допустимому workflow доски.  
- Исполнитель должен иметь доступ к workspace/project/board.  

---

### 5.5. Комментарии

**Требования:**

- Добавление комментария к задаче.  
- Удаление/редактирование комментария (с учётом прав).  
- Просмотр списка комментариев задачи.  

---

### 5.6. Теги

**Требования:**

- Создание тегов.  
- Привязка тегов к задачам.  
- Фильтрация задач по тегам.  

---

### 5.7. История изменений (Audit)

**Требования:**

- Запись изменений задачи:  
  - кто изменил  
  - что изменил  
  - старое значение  
  - новое значение  
  - время изменения  
- Просмотр истории изменений задачи.  

Каждая **запись аудита** — это отдельная сущность.

Она содержит:

- ID
- taskId
- userId
- timestamp
- fieldName (например, status, priority, assignee)
- oldValue
- newValue
- context (workspaceId, projectId, boardId)

**Инварианты:**

- История должна сохраняться при любых изменениях ключевых полей задачи (статус, приоритет, исполнитель, описание).

---

## 6. Архитектурные решения

### 6.1. Слоистая архитектура

**Слои:**

- **Domain** — сущности, value objects, доменные правила, инварианты, доменные события.  
- **Repository** — интерфейсы доступа к данным, работа с БД.  
- **Service** — бизнес‑логика, сценарии использования, транзакции, проверка прав.  
- **Controller** — REST API, DTO, валидация, HTTP‑ответы.  
- **Mapper** — преобразование DTO ↔ Domain (MapStruct).

**Принципы:**

- Domain не знает о HTTP, БД, Security.  
- Service не знает о DTO и HTTP.  
- Controller не содержит бизнес‑логики.  
- Repository не содержит бизнес‑логики.  

---

### 6.2. Доменные модели и инварианты

**Примеры доменных правил:**

- `Workspace` не может быть создан без владельца.  
- `Project` не может быть создан вне workspace.  
- `Board` не может быть создан вне проекта.  
- `Task` не может быть создан вне board.  
- `Task.changeStatus()` проверяет допустимость перехода статуса.  
- `Task.assignTo(user)` проверяет доступ пользователя к board/project/workspace.  

---

### 6.3. Domain Events

**Примеры событий:**

- `TaskCreatedEvent` — задача создана.  
- `TaskStatusChangedEvent` — статус задачи изменён.  
- `TaskAssignedEvent` — задача назначена исполнителю.  

**Назначение:**

- аудит  
- уведомления  
- интеграции (в будущем)  

---

### 6.4. Безопасность

**Решения:**

- JWT‑аутентификация.  
- Использование Spring Security OAuth2 Resource Server для валидации JWT.  
- Ролевые модели на уровне workspace/project/board.  
- Проверка прав в сервисах перед выполнением операций.  

---

### 6.5. Работа с данными

**Решения:**

- PostgreSQL как основная БД.  
- Миграции схемы через Liquibase/Flyway.  
- Индексы по workspace/project/board/task для эффективной фильтрации.  

---

### 6.6. Тестирование

**Решения:**

- Unit‑тесты доменных методов и сервисов.  
- Интеграционные тесты контроллеров и репозиториев.  
- Тестирование безопасности (доступ/недоступ).
